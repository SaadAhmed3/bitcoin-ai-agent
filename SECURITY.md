# Security — BTC Signal Lab 0.9.0

## Threat model

BTC Signal Lab is a **local, single-user** research app. It runs on your own Windows PC, serves a dashboard on `http://127.0.0.1:<port>` and has **no login**. It holds no exchange keys and cannot trade. The only secret it may know is an optional, free CoinGecko Demo key in `.env`.

| Who / what | In scope? | Defence |
|---|---|---|
| A **malicious website** open in the same browser, sending requests to `127.0.0.1:<port>` (CSRF) | Yes, the main remote threat | State-changing requests need a same-origin `Origin`/`Referer` or the custom header `X-Requested-With: BTCSignalLab`; a cross-site page cannot send that header without a CORS preflight, which the app never approves |
| A website that points its own domain at 127.0.0.1 (**DNS rebinding**) to read the API | Yes | `Host` allow-list: only `localhost`, `127.0.0.1`, `[::1]` (on the app's port) and names you add to `APP_ALLOWED_HOSTS` |
| **Hostile content from data sources**: RSS headlines/links, alert text, AI model output | Yes | All dynamic text is escaped in the browser; links from data must be `http(s)://` or a same-site path; a strict Content-Security-Policy blocks inline and foreign scripts; headlines are quoted to the AI as untrusted data |
| Other devices on your network | Yes, by default excluded | Binds to `127.0.0.1`; network exposure needs `APP_ALLOW_REMOTE=1` and prints a warning; the Flask debugger is never enabled on a non-loopback address |
| Accidental leakage of the API key | Yes | Key stays in `.env` (gitignored); shown only as "set"/"not set"; never in pages, API responses, exports, logs or the database |
| Real-money loss through the app | Yes | No order code, no exchange keys, no withdrawal/futures/leverage code; the paper account is SIMULATED and the database rejects non-simulated orders |
| Malware or another user **already running code on your PC** | No | Such code can read the SQLite file and `.env` directly; nothing an app-level control can stop |
| Supply-chain compromise of PyPI packages | Partly | Exact versions pinned; `pip-audit` clean at release; no other mitigation |

### Accepted risks

- **No authentication.** By design for a single-user local tool. Mitigated by the loopback bind, the Host allow-list and the CSRF guard. Do not set `APP_ALLOW_REMOTE=1` on an untrusted network.
- **`style-src 'unsafe-inline'`** in the CSP. Plotly and a few inline `style=` attributes need it. Scripts stay `'self'` only, so this does not allow script injection.
- **Plain HTTP on loopback.** Traffic never leaves the PC; TLS would add certificate handling for no gain.
- **Local programs can send the CSRF header.** Any program already running on the PC can call the API (or read the database directly); that is outside the threat model.
- **Rate limits are per process and in memory.** They reset on restart; they exist to stop accidental loops and abuse from a hostile page, not a determined local user.
- **SQL migration f-string** (row 5): column names come from a constant list.
- **The SQLite file is not encrypted.** It holds market data, news, signals, the SIMULATED account and chat history, and no secrets.

## Reporting a security issue

This is a personal research project with no bug-bounty programme. If you find a problem:

1. Do **not** post exploit details publicly first.
2. Contact the maintainer privately (the e-mail of the project owner), with the version (`GET /api/health`), the steps to reproduce and the impact.
3. Expect an acknowledgement within 7 days. Fixes get a test and a CHANGELOG entry.

If you only use the app yourself: keep it on `127.0.0.1`, keep `.env` private, and run `python -m pip_audit -r requirements.txt` from time to time.
